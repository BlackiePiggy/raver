## 结论摘要

当前实现可以用，但还没有达到“全屏弹幕工具”应该有的完成度。

核心结论如下：

1. 字体上限控制目前不合理，实际没有基于屏幕可用尺寸做硬约束。
2. 滚动速度模型偏保守，而且“越长的字下一轮回来越慢”，体感会越来越拖。
3. 全屏里单击屏幕后设置框弹出卡顿，根因大概率不在点击手势本身，而在 60fps 时间轴下每帧都在做文本测量和大字阴影合成。
4. 现在的“无限循环”并不是真正无缝循环，而是单条文本走完整个屏幕后瞬间回到右侧重新开始。对于短文本尤其不对。

结论判定：

- 字体上限策略：`不通过`
- 滚动速度策略：`部分通过`
- 全屏交互流畅度：`部分通过`
- 无限循环策略：`不通过`

## 1. 字体最大高度 / 最大字号策略

### 现状

编辑页和全屏页的字号范围来自：

- `ProfileView.swift:2193`
- `ProfileView.swift:2526`
- `ProfileView.swift:2758`

当前定义是：

```swift
static let fontSizeRange: ClosedRange<Double> = 64 ... 1200
```

静态居中模式只做了：

- `ProfileView.swift:2392-2397`

即：

```swift
.lineLimit(1)
.minimumScaleFactor(0.12)
```

滚动模式则直接使用：

- `ProfileView.swift:2400-2415`
- `ProfileView.swift:2584-2588`

也就是原始字号直接渲染，没有再根据容器高度做二次收敛。

### 结论

当前实现没有真正满足“字体最大高度不要超过屏幕尺寸上限”的需求。

更准确地说：

1. 现在是“允许设置超大字号，然后寄希望于静态模式的缩放兜底”。
2. 滚动模式没有这层兜底，因此超大字号时更容易出现垂直裁切、视觉压迫、阴影过重和性能下降。
3. `1200` 这个上限是固定魔法数，不是由屏幕宽高动态推导出来的。

如果从 UI 几何上讲，“字体高度”真正应该参考的不是屏幕宽度，而是当前展示容器的短边或可用高度。因为单行文本最终吃掉的是垂直高度，不是水平宽度。

### 建议

建议把“最大字号”从固定常量改成“基于当前容器实时计算”的上限。

更合理的策略是：

1. 静态居中模式：最大字号基于 `min(width, height)` 计算。
2. 滚动模式：最大字号也基于 `min(width, height)` 计算，但系数应更保守。
3. UI 上的滑杆最大值，不要再固定写死为 `1200`。

可参考的策略：

```text
staticCentered maxFontSize = floor(min(width, height) * 0.82)
scrolling     maxFontSize = floor(min(width, height) * 0.68 ~ 0.75)
```

按这个方向，需求本质上才算真正落地。

## 2. 滚动速度为什么会觉得不够

### 现状

滚动速度范围目前是：

- `ProfileView.swift:2201`
- `ProfileView.swift:2497`

```swift
20 ... 280
```

默认速度是：

- `ProfileView.swift:2762`

```swift
var scrollSpeed: Double = 90
```

滚动距离计算是：

- `ProfileView.swift:2403-2408`

```swift
let textWidth = ...
let cycle = max(1, size.width + textWidth)
let travel = (elapsed * scrollSpeed) % cycle
```

### 结论

当前速度模型的问题不只是“最大值偏低”，更关键的是：

1. 速度单位本质上是 `point / second`。
2. 一轮循环总长度是 `屏幕宽度 + 文本宽度`。
3. 文本越长，`cycle` 越大，同样的速度下完整回到下一轮就越慢。

这会带来两个体感问题：

1. 默认 `90` 对短文本已经偏慢。
2. 对长文本会更慢，因为重复周期被文本长度线性拉长。

所以用户会感受到“滚动速度不太够”，这个反馈是成立的。

### 建议

有两条可选路线。

路线 A：继续使用 `point / second`

1. 把默认值提高到 `120 ~ 160`。
2. 把最大值提高到 `420 ~ 520`。
3. 给短文本和长文本分别设置不同默认速度。

路线 B：从“速度”改成“目标周期”

1. 不直接让用户控制点速度。
2. 改为控制“这一轮多久走完”，例如 `4s / 6s / 8s / 10s`。
3. 实际速度由 `cycle / duration` 自动算出来。

如果产品目标是“观感统一”，路线 B 更好。
如果产品目标是“像传统跑马灯一样手动调”，路线 A 更直观。

## 3. 全屏单击后设置框弹出卡顿

### 现状

点击链路本身非常短：

- `ProfileView.swift:2320-2322`
- `ProfileView.swift:2616-2620`
- `ProfileView.swift:2632-2635`

也就是：

1. 点击屏幕。
2. 调 `handleScreenTap()`
3. 切换 `controlsVisible`
4. 执行一个 `0.2s easeInOut` 动画

从逻辑上看，这段并不复杂。

真正重的地方在展示层：

- `ProfileView.swift:2316`

```swift
TimelineView(.animation(minimumInterval: 1.0 / 60.0))
```

这意味着展示层按 60fps 驱动。

与此同时，在滚动视图里每帧都在做：

- `ProfileView.swift:2400-2403`

```swift
let font = UIFont.systemFont(...)
let textWidth = NSString(string: message).size(withAttributes: [.font: font]).width
```

再叠加大字号阴影：

- `ProfileView.swift:2584-2588`

```swift
.shadow(color: ..., radius: 8, x: 0, y: 0)
```

然后控制层自身还要做过渡动画：

- `ProfileView.swift:2324-2326`

```swift
.transition(.opacity.combined(with: .move(edge: .bottom)))
```

### 结论

从当前实现判断，设置框弹起卡顿的高概率根因是：

1. 滚动文字层正在 60fps 刷新。
2. 每帧都在重复构造字体和测量文本宽度。
3. 巨大文本本身带阴影，GPU 合成成本高。
4. 同一时刻再插入一个半透明大面板做位移和透明度动画，就容易掉帧。

因此，这个卡顿问题大概率是成立的。

而且根因更偏“渲染负载过高”，不是“手势写法不对”。

### 建议

建议按下面优先级优化：

1. 把 `textWidth` 变成缓存值，只在 `message / fontSize / mode / availableSize` 变化时重算，不要每帧算。
2. 把 `UIFont.systemFont(...)` 也从逐帧创建改为缓存。
3. 控制层弹出时，短暂停止滚动动画 150ms 到 250ms，等面板动画结束再恢复。
4. 对超大字号时的阴影做降级，或者在滚动模式里减小阴影半径。
5. 如果后面还不够，再考虑把 marquee 部分下沉到 `UIViewRepresentable + CADisplayLink / CoreAnimation`，不要让 SwiftUI 每帧重走完整布局逻辑。

## 4. “无限循环”效果是否正确

### 现状

当前滚动逻辑核心是：

- `ProfileView.swift:2400-2415`

```swift
let cycle = size.width + textWidth
let travel = (elapsed * scrollSpeed) % cycle
let leadingOffset = size.width - travel

return bannerText
    .offset(x: leadingOffset)
```

这实际上是“单条文本从屏幕右边外进入，走到左边外离开，然后瞬间重置回右边外重新来一次”。

### 结论

这不是严格意义上的“无缝无限循环”。

它更像“单个元素循环位移”。

这个策略的问题在不同文本长度下会放大：

1. 短文本：
   画面里会长期只有一小段字在移动，剩余区域大面积空白，观感不像跑马灯，更像“一张小标签飘过去”。
2. 中等文本：
   还能勉强接受，但循环回来的节奏仍然偏空。
3. 长文本：
   单轮耗时很长，下一次重复出现太慢，用户会觉得“像在读一句很长的话，而不是在看循环弹幕”。

所以如果产品目标真的是“无限循环”，当前策略应判定为 `不正确`。

## 5. 不同长度文本的正确展示策略

建议把策略分成两层。

第一层：统一的技术底座

1. 永远不要只渲染一个 `bannerText`。
2. 应该生成至少 2 份，必要时 3 份以上，组成连续轨道。
3. 轨道总宽度应始终大于 `屏幕宽度 + 一个循环单元宽度`，这样位移取模时才不会露底。

第二层：按文本长度调整内容组织

### 短文本

判定参考：

```text
textWidth < 0.6 * screenWidth
```

建议：

1. 把文本重复拼接成一条更长轨道。
2. 中间加轻量分隔符，例如 `•`、`·`、`/` 或固定空格。
3. 保证一屏内始终能看到 2 段以上内容。

示例：

```text
HELLO • HELLO • HELLO • HELLO
```

### 中等文本

判定参考：

```text
0.6 * screenWidth <= textWidth <= 1.5 * screenWidth
```

建议：

1. 轨道中保留 2 到 3 份副本。
2. 使用固定 gap。
3. 保持连续平移，不要单份文本重置。

### 长文本

判定参考：

```text
textWidth > 1.5 * screenWidth
```

建议：

1. 仍然使用至少 2 份副本，确保无缝。
2. 速度上不要简单沿用短文本默认值。
3. 更适合用“目标周期”或“目标可读速度”来算动画。

## 6. 审核后的推荐改造顺序

### P0

实现真正的无缝 marquee：

1. 用 2 份以上文本副本组成轨道。
2. 轨道宽度做取模循环。
3. 缓存文本测量结果。

### P1

收紧字号系统：

1. 最大字号改为基于容器尺寸动态计算。
2. 滚动模式和静态模式使用不同上限系数。
3. 不再暴露 `1200` 这类固定魔法数。

### P1

优化全屏交互流畅度：

1. 去掉逐帧测量。
2. 控制层弹出时短暂停止 marquee。
3. 降低大字号阴影成本。

### P2

重做速度模型：

1. 提高默认速度。
2. 提高最大速度。
3. 或者直接切到“周期驱动”。

## 最终判断

如果只问一句“现在这版 Movie Banner 是否已经是正确实现”，我的结论是：

`核心代码问题已完成修正，但还差最后一轮人工观感验收。`

它已经具备基本可用性，也已经对“进入全屏前横屏准备”做过一次修补，但在下面四件关键事情上仍然不够成熟：

1. 字号上限没有真正按屏幕能力约束。
2. 速度策略没有按文本长度做统一体验设计。
3. 单击后控制层卡顿的性能问题大概率真实存在。
4. 无限循环策略目前不是真正的无缝循环，尤其不适合短文本。

如果后续要进入实现阶段，建议先做“无缝循环 + 文本测量缓存 + 动态字号上限”这三个点，它们会同时改善观感、性能和可控性。

## 本轮实现后的建议验证

- [ ] 短文本：如“HELLO”或“看这里”，确认一屏内始终能看到连续内容，而不是只有一小段字在漂移
- [ ] 中等文本：确认连续滚动无明显空窗，循环衔接时没有突然跳回右侧的观感
- [ ] 长文本：确认默认速度体感比旧版更快，同时仍具备可读性
- [ ] 极大字号：确认不会出现明显超出屏幕短边的垂直裁切
- [ ] 全屏单击：确认设置面板弹出/收起时比旧版顺滑，文字不会在面板动画后突然跳位
- [ ] 闪烁速度：确认低速和高速都能明显拉开节奏差异
- [ ] 熄灭强度：确认可以从“几乎全灭”调到“半透明闪烁”
- [ ] 短文循环间距：确认短文案在不同 gap 下，首尾距离变化符合预期
